# Feature: Exclude machine-generated companion theorems from spec bookkeeping

## Summary

Some verification-framework attributes elaborate a tagged theorem into an extra
machine-generated theorem alongside it. The known case is Aeneas's `@[step]`:
for `theorem X`, it adds an mvcgen-shaped wrapper `X.mvcgen_spec` whose
declaration range is registered from the original theorem's syntax. probe-lean
currently treats the companion as a first-class atom: it lands in every
dependency's `specs` list next to the real spec, and (because its source range
points at the parent's attribute line) the source-scan attribute fallback
misattributes the parent's `@[step]` to it. With two `@[step]`-tagged specs per
function, every primary-spec signal fails — the known-attribute signal requires
exactly one match and sole-spec inference requires exactly one spec — so fully
proved functions end up with no `primary-spec`, and downstream probe-aeneas
colors their Rust implementations "unverified". This feature detects such
companions, flags them `is-lean-generated` + `is-hidden` (like `deriving`
clusters and projections), and excludes lean-generated theorems from `specs`
and primary-spec computation.

Motivating case: SymCRust-lean, where 200 translated Rust functions carry
exactly the `{X.spec, X.spec.mvcgen_spec}` pair and render yellow instead of
green on VeriLib (probe-lean#84).

## Requirements

- [ ] New helper `generatedCompanionTheoremNames` in `ProbeLean/Analysis.lean`
      (next to `derivedInstanceClusterNames`): returns the names of theorems
      that qualify as machine-generated companions.
- [ ] A theorem whose name is `<parent>.mvcgen_spec` qualifies based on what
      `parent` is among the analyzed declarations. The name shape is the
      whole signal: corroborating via a dependency edge to the parent is
      impossible — the wrapper references its parent only in the *proof
      term*, and theorem proof bodies are not visible in the imported
      environment (theorem term-dependencies come out empty), so the edge
      cannot be observed. The cases:
  1. `parent` is a **theorem** → generated companion (the parent is the real
     spec and is collected into `specs` itself);
  2. `parent` is **absent** → generated companion (`attribute [step]` applied
     to an *external* theorem, e.g. `Aeneas.Std.U32.add_bv_spec`, generates
     the companion in the tagging project module while the parent stays
     outside the project);
  3. `parent` is an **axiom** → NOT flagged. `@[step] axiom X.spec` generates
     the same companion, but axioms are never collected into `specs` lists,
     so the companion is the specified def's *only* spec-shaped edge — the
     axiom's proxy. Excluding it would orphan every axiom-specified def
     (SymCRust-lean: 19 defs carry such a companion as primary spec).
  4. `parent` is any other kind (e.g. a def) → NOT flagged (conservative;
     `@[step]` only elaborates theorems and axioms).

  Source ranges and modules are deliberately **not** consulted: the
  `attribute [step] thm₁ thm₂` command form registers the companion's range
  from the *attribute command's* syntax, which lies outside the parent
  theorem's range, so a range-containment check produces false negatives for
  exactly the declarations this feature targets.
- [ ] The marking loop in `runAnalysisViaLakeEnv` flags detected companions
      `isHidden := true, isLeanGenerated := true`, exactly like derived
      instance clusters and projections. They are **not dropped**: they stay
      in the atom set and dependency graph so transitive-verification
      contamination still flows through them.
- [ ] `computeSpecs` skips theorems with `isLeanGenerated` when building the
      `specs` reverse map, removing them from the heuristic primary-spec
      signals (known-attribute, `_spec` suffix, sole-spec) — a
      machine-generated theorem is never inferred to be a user spec. The
      explicit `@[primary_spec]` tag (signal 0) deliberately still honors
      generated theorems: it is the user's escape hatch, including for a
      false positive of this detection.
- [ ] Docs updated: the `is-lean-generated` wording in `docs/USAGE.md` /
      `docs/SCHEMA.md` / `README.md` extends from "deriving clusters and
      projections" to include attribute-generated companion theorems;
      `CHANGELOG.md` gets an Unreleased entry.
- [ ] Tests in `Tests/Main.lean` cover detection and exclusion (see
      Acceptance Criteria).

## API / Interface Design

No new CLI flags, config keys, or schema fields. New internal helper:

```lean
/-- Names of attribute-macro-generated companion theorems (`X.mvcgen_spec`
    generated by Aeneas's `@[step]` for a tagged `theorem X`). -/
def generatedCompanionTheoremNames (decls : Array DeclInfo) : Std.HashSet Name
```

`computeSpecs` behavior change is internal: lean-generated theorems no longer
appear in `specs` arrays or as `primary-spec` values in the JSON output.

## Behavior

### Normal operation

For SymCRust-style input —

```
theorem X.spec              @[step], lines 372–405, Properties/….lean
theorem X.spec.mvcgen_spec  generated, range 376–376 (the parent's attr line)
def    X                    Code/….lean, depends on nothing here;
                            both theorems depend on X
```

— the companion is flagged generated+hidden; `X.specs = [X.spec]`;
the known-attribute signal sees exactly one `@[step]` candidate (or sole-spec
fires) and `X.primary-spec = X.spec`.

### Edge cases

- **`attribute [step] thm₁ thm₂` command form**: companions' ranges point at
  the attribute command line, outside the parents' ranges — still flagged
  (parent theorems exist in the project).
- **`attribute [step]` on an external theorem** (`Aeneas.Std.*`): companion
  is a project decl, parent is not a project atom — flagged.
- **`@[step] axiom X.spec`**: companion NOT flagged — it is the axiom's spec
  proxy (see Requirements). Note the proxy is an ordinary theorem proved
  *from* the axiom, so it can be `transitively-verified` while the axiom
  itself is `trusted` — matching the system-wide semantic that
  transitively-verified means "proved relative to the trust base" (trusted
  atoms do not contaminate). Follow-up question, out of scope: whether
  axioms should be collected into `specs` lists directly, which would let
  these companions be flagged too.
- **Parent exists but is a def** (a hand-written `foo.mvcgen_spec` next to a
  def `foo`): not flagged.
- **Hand-written theorem named `<theorem>.mvcgen_spec`**: flagged. Accepted
  false positive — the name shape is Aeneas machinery convention, the
  consequence (hidden + excluded from heuristic spec bookkeeping, still in
  the graph) is mild, and tagging it `@[primary_spec]` restores it as
  primary spec (the escape hatch).
- **Contaminated companions**: the existing `unhideContaminatedGenerated`
  pass applies unchanged — a companion that is not transitively verified is
  unhidden for tracing.
- **Companion carrying `@[primary_spec]` via the tag attribute**: wins
  signal 0 like any explicitly tagged theorem. The tag applies to exact
  names, so it can only appear on a companion by deliberate user action
  (`attribute [primary_spec] X.spec.mvcgen_spec`) — silently ignoring the
  strongest explicit signal would remove the escape hatch.

## Non-Goals

- Does NOT attempt generic detection of macro-generated theorems — only the
  `.mvcgen_spec` name shape with the corroborating parent-dependency check.
  Other frameworks' companions can be added when observed.
- Does NOT change the source-scan attribute fallback. Companions may still
  show the parent's attributes in their `attributes` array; harmless once
  they are excluded from spec bookkeeping and hidden.
- Does NOT add a config knob for companion suffixes.
- Does NOT change verification-status assignment, enrichment, or the
  dependency graph.
- Does NOT add a namespace-tolerant naming signal (suggested in review:
  deduce that `symcrust.const_time_array_copy.spec` specifies
  `symcrust.common.const_time_array_copy` despite the namespace mismatch).
  That is the namespace-mismatch case the primary-spec-heuristic spec
  already deferred; it needs its own uniqueness/ambiguity design and its
  place in the precedence chain — a follow-up, sized by this feature's
  validation residue.

## Acceptance Criteria

- [ ] Unit tests for `generatedCompanionTheoremNames`: theorem-parent pair
      detected (inline and attribute-command ranges); missing-parent
      companion detected; axiom-parent and def-parent companions not
      detected; name-shape match without an observable parent dependency
      still detected (proof bodies are invisible; accepted false positive).
- [ ] Unit tests for `computeSpecs`: a def with a real `@[step]` spec plus a
      lean-generated `@[step]` companion gets `specs = [real spec]` and
      `primary-spec = real spec`; a lean-generated theorem is never emitted
      as a `specs` entry; an explicit `@[primary_spec]` on a generated
      theorem still wins signal 0.
- [ ] Existing tests pass unchanged.
- [ ] Validation on SymCRust-lean (Lean v4.31.0 build): `Symcrust.Code` defs
      with `{X.spec, X.spec.mvcgen_spec}` pairs get `primary-spec = X.spec`;
      the count of Code defs with a `primary-spec` rises from 11 to the
      hundreds; `.mvcgen_spec` atoms are `is-lean-generated` + `is-hidden`
      and absent from all `specs` arrays.
