# Audit scripts

Measurement scripts for probe-lean's dependency graph, written for issue #99
(dependency edges hidden under auxiliary constants) and reusable on any target
project.

They live in lowercase `tools/` deliberately. `Tools/` is a `lean_lib` and these
must stay **out of probe-lean's build**: they run under the *target* project's
toolchain, not probe-lean's pinned one, because reading a project's `.olean`
files requires the Lean version that wrote them.

They also duplicate five helpers from `ProbeLean/Analysis.lean` on purpose
(`autoGeneratedSuffixes`, `containsSubstring`, `isInternalName`, `valueOf`, and
a closure walk). An oracle that imports the code it checks cannot catch a bug in
that code.

## Running them

From the target project, under the target's toolchain:

```bash
cd <target-project>
env -u LEAN_PATH bash -lc 'source ~/.elan/env; \
  lake env lean --run <probe-lean>/tools/audit/Audit.lean <ModulePrefix>...'
```

`<ModulePrefix>...` is the project-module filter — the same set `extract`
analyzes (e.g. `Curve25519Dalek`). Each run costs a few minutes,
dominated by importing the project's transitive `.olean` closure (Mathlib, if
present).

## What each script measures

| Script | Question it answers |
|---|---|
| `Audit.lean` | Per-project totals: how many emitted atoms reference an auxiliary, how many project-internal edges are hidden underneath, how many atoms gain in-edges, and how many go from in-degree 0 to non-zero. |
| `Audit2.lean` | Taint divergence: run `sorry` contamination over the emitted graph and over the aux-folded graph, and report the atoms whose `verification-status` is therefore wrong today. |
| `Audit3.lean` | Prevalence of embedded proofs per corpus (core, Batteries, Mathlib, Aeneas, the project): what fraction of non-theorem declarations carry one. Answers "is this an edge case?". |
| `Audit4.lean` | Histogram by auxiliary *shape* (`_proof_N`, `match_N`, `.mk`, `.injEq`, …) of how many project and external edges each shape hides, and how many distinct hosts it affects. This is what sized the structural-member follow-up. |
| `Audit5.lean` | Type-vs-value split: are the hidden auxiliaries in a declaration's type or its body? Type-position folding changes `typeDependencies`, which `computeSpecs` walks, so it has a `specs`/`primary-spec` blast radius. |
| `Audit6.lean` | **Oracle for the shipped fold.** Re-derives, per atom and per bucket, exactly which targets the shipped predicate should add, and prints them as `<atom>\t(type\|term)\t<target>` TSV. Independent implementation: the classification is written out by hand and the traversal has **no cross-root cache**, which is the machinery most likely to be wrong in the shipped version. |
| `compare-extract.py` | **Invariant gate.** Diffs a before/after pair of `extract` artifacts and asserts that the fold only added entries to `type-dependencies`/`term-dependencies`, left the `*-external` arrays byte-identical, did not change the atom set, kept `dependencies` the deduplicated union of the two buckets, and moved `verification-status` only in the one direction adding edges can cause. With `--oracle` it also requires the added edges to be exactly what `Audit6.lean` predicts. |

`Audit.lean`–`Audit5.lean` fold **every** filtered class, including structural
members. They measure the size of the problem, not the shipped behaviour. Only
`Audit6.lean` matches what probe-lean actually does.

## The verification recipe

```bash
# 1. before/after artifacts, same project, same module filter
<baseline-probe-lean> extract <target>   # keep the artifact
<new-probe-lean>      extract <target>   # keep the artifact

# 2. the oracle, on the same project state
cd <target>
env -u LEAN_PATH bash -lc 'source ~/.elan/env; \
  lake env lean --run <probe-lean>/tools/audit/Audit6.lean <ModulePrefix>...' \
  > /tmp/oracle.tsv

# 3. the gate
<probe-lean>/tools/audit/compare-extract.py before.json after.json \
  --oracle /tmp/oracle.tsv
```

The gate is the invariants plus oracle agreement, **not** the edge counts below:
recovering the wrong 565 edges would pass any numeric test. An oracle derived
from the same contract cannot validate that contract either, so the counts are
context for reviewers rather than an acceptance criterion.

## Baseline numbers

Target: `curve25519-dalek-lean-verify`, freshly built, Lean 4.31.0, Mathlib
cache fetched, module filter `Curve25519Dalek`, 2354 emitted atoms.
Measured with the "fold everything" scripts (`Audit.lean`–`Audit5.lean`).

| | |
|---|---|
| non-theorem decls carrying an embedded proof (`Audit3`) | 164 / 957 (17%); Mathlib itself 41% |
| atoms losing ≥1 project-internal edge (`Audit`) | 191 |
| project-internal edges dropped (`Audit`) | 565 |
| type vs. value position of those edges (`Audit5`) | 2 type / 563 value |
| project atoms losing in-edges (`Audit`) | 216 (133 theorems) |
| project theorems that look unreferenced but are used (`Audit`) | 62 |
| atoms given a wrong clean `verification-status` (`Audit2`) | 6 (the `*_loop_spec` family, 4 `sorry` roots) |
| structural-member share of the dropped edges (`Audit4`) | `.mk` 153, `.injEq` 7, `.casesOn` 1, `.eq_N` 1 |

The last row is why structural members are excluded from the shipped fold and
tracked as a follow-up: mapping a type's members onto their parent atom is a
different change, and `.eq_N` generalisation would alter atom *emission*.

The shipped predicate is not a subset of those 565, so the counts are not
comparable end to end: it excludes structural members (about 162 of the 565) but
also folds through project members that have no declaration range — Aeneas's
`*_loop.mutual` helpers, for instance — which the "fold everything" scripts
never traversed. What it actually did on the same project:

| | |
|---|---|
| dependency edges recovered | 593 (575 term, 18 type) |
| atoms affected | 157 |
| atoms going from in-degree 0 to non-zero | 65 |
| `transitively-verified` → `verified` | 6 (the `Audit2` prediction, exactly) |
| `specs` / `primary-spec` field changes | 6, including one detached `primary-spec` |
| node expansions / edges scanned / cached names | 4653 / 349k / 6208 |
| extract wall-clock (steady state, mean of 3) | 8.87 s → 10.07 s (+1.20 s) |
| peak RSS | 6870973 kB → 6872725 kB (+0.03%) |

## Hand-checked expectations

The case that started the issue, kept as a worked example because it is checkable
by eye rather than by the same traversal the oracle uses:

- `curve25519_dalek.math.sqrt_checked` discharges a proof obligation with a
  tactic block that applies `curve25519_dalek.math.sqrt_m1_not_square`. Lean
  abstracts the obligation, so the emitted graph carried no
  `sqrt_checked → sqrt_m1_not_square` edge at all — the reason a reporter read
  the lemma as unreferenced, cut it from a bundle, and broke `lake build`.

  Measured on the commit above: `sqrt_m1_not_square` had **1** in-edge before the
  fold (from `field.FieldElement51.SQRT_M1_not_square`, which names it directly)
  and **6** after, the new five being `sqrt_checked`, `sqrt_checked_spec`,
  `sqrt_checked_iff_isSquare`, `edwards.EdwardsPoint.v_coord_birational_match`
  and `Montgomery.Aux_u_affine_toPoint_spec`. All five reach it only through an
  abstracted proof obligation.
