# CLAUDE.md

This file guides Claude Code (claude.ai/code) in this repository.

## Spec-Driven Development Workflow

This project uses spec-driven development. Follow this workflow:

### When the user asks you to implement a feature:

1. **Check for a spec first**: Look in `specs/active/` for a spec file
2. **If no spec exists**: Ask the user to write one, or offer to draft one together
3. **If spec exists**: Read it completely before proceeding
4. **Enter plan mode**: Create an implementation plan based on the spec
5. **Wait for approval**: Do not implement until the user approves the plan
6. **Implement**: Follow the spec strictly. Do not add unrequested features

### When reviewing or drafting specs:

- Make sure that requirements are testable and unambiguous
- Identify missing edge cases
- Flag any contradictions or unclear points
- Keep scope minimal. A spec describes one coherent feature

### Spec file locations:

- `specs/template.md` - Template for new specs
- `specs/active/` - Local working specs for the current work

The tree does not keep completed specs. Git history and the PR keep them.

## Documentation

## Commands

```bash
lake build                      # Build the project
lake build tests                # Build tests
.lake/build/bin/tests           # Run tests
probe-lean extract <PATH>       # Atoms with dependencies, specs and verification status
probe-lean check-axioms <PATH>  # List project constants that rest on an unexcused sorry, then the trusted base
probe-lean viewify <PATH>       # Filter extract output → molecules for web UI
```

## Testing

- Unit tests are in `Tests/Main.lean`. They need no external tools.
- **Tests must be added** for each new feature. Run them before committing. All tests must pass before merging.
- To add a test, define `def testYourFeature (result : TestResult) : IO TestResult`, check each condition with `result ← test "description" condition result`, and call the function from `runSuiteA` or `runSuiteB`. `main` only calls those two.
- `examples/lean_ExampleProject_0.1.0.json` is generated by `tools/gen-fixture.sh` through the real `Envelope` and `UnifiedAtomsOutput` serializers. Do not edit it by hand. After any output-format change (new field, renamed key, version bump), run `./tools/gen-fixture.sh` and commit the result.

CI (`.github/workflows/ci.yml`, on push and PR to `main`) runs these jobs:

- `build`: builds the project.
- `shell-tests`: the Lean version-policy and installer helper tests.
- `test`: the unit suite and end-to-end `extract` and `check-axioms` checks. The checks run on the Lake projects in `tests/fixtures/` (`aux-fold`, `collision`, `merge`, `cross-merge`, `module-merge`, `module-collision`, `orphan`). The job also regenerates the example fixture and fails on any diff.
- `test-newest`: the same suite and fixture checks on the newest supported Lean (`LEAN_VERSION` in the job).
- `check-version`: `ProbeLean/Version.lean` matches `lakefile.toml`.
- `check-extract`: runs `probe-extract-check` on the example fixture.
- `auto-tag`: if a push to `main` passes all other jobs and the tag does not exist, it creates the tag `v<version>`.

## Build performance and elaboration depth

Check the effect of every change on `lake build` time. Each `x ← ...` bind in a `do` block nests one more `>>= fun ... =>`, and elaboration cost grows superlinearly with that depth. One function with 100+ binds took 10+ minutes to compile. The same tests split into small functions took under 2 seconds.

1. **Keep a `do` block under about 30 binds.** If a function grows past that, extract a helper.
2. **`Tests/Main.lean` uses one function per test section.** `main` calls `runSuiteA` and `runSuiteB`, which hold only `result ← testXxx result` calls. When a suite grows too long, add another `runSuiteX` instead of inlining test logic.
3. **Never add `set_option maxRecDepth`** to work around slow compilation. Split the `do` block instead.
4. **Prefer `Id.run do` for pure computations** over lifting into `IO`.
5. **Measure before and after.** Compare `lake build` times for non-trivial logic. Investigate an incremental regression of more than a few seconds.

## Running extract on target projects

`probe-lean extract <target-project>` builds the target and skips the build if the build cache is up to date. If the target depends on Mathlib and has no Mathlib cache, extract downloads it (`ensureMathlibCache` in `ProbeLean/Extract.lean`). The probe-lean binary must match the target's Lean version. The installer picks it with `--from-project`. See [docs/usage.md](docs/usage.md).

## Versioning

The version is defined **once** in `lakefile.toml` and generated into `ProbeLean/Version.lean` by `tools/gen-version.sh`. After bumping the version in `lakefile.toml`, run `./tools/gen-version.sh` and commit both files. CI checks they stay in sync.

Do **not** hardcode version strings anywhere else. Use `ProbeLean.version` (or `Constants.toolVersion`, which references it).

**When to bump the version:** If a release includes new features, a changed output format, or breaking changes to the CLI or installer, bump the minor version in `lakefile.toml` and regenerate. Patch bumps are for bug fixes only. Update `CHANGELOG.md` with the new version entry before committing. Tag the commit with `v<version>` to trigger the release workflow.

## Architecture

### Extract pipeline

`probe-lean extract` runs: `build → atomize (+ kernel taint pass) → markAtomFlags → specs → verify (log cross-check) → merge (status from the taint pass) → enrich (graph cross-check) → envelope → write`

- `ProbeLean/Main.lean`: CLI entry point for `extract`, `check-axioms` and `viewify`.
- `ProbeLean/Extract.lean`: orchestrates the pipeline and produces `UnifiedAtom` output.
- `ProbeLean/CheckAxioms.lean`: the `check-axioms` command. It runs the same taint pass as `extract` and prints the tainted constants and the trusted base T.
- `ProbeLean/Analysis.lean`: walks the Lean environment, extracts type and term dependencies, and computes the `codomain-*` facts.
- `ProbeLean/Atomize.lean`: converts declarations to `Atom` structs, applies the filtering flags, and runs the taint pass after import.
- `ProbeLean/Taint.lean`: the kernel taint pass. It builds the project constant set P, computes T, runs the walk, and formats the diagnostics.
- `ProbeLean/AxiomCheck.lean`: the `sorryAx` reachability walk with a blocked set and a shared memo.
- `ProbeLean/Trust.lean`: the three trust rules (`axiom`, `externally_verified`, `*External` module), the only place they are written.
- `ProbeLean/TagSet.lean`: reads the `@[externally_verified]` tag set statically from the target's olean entries.
- `ProbeLean/Transitive.lean`: applies the taint pass result to atoms (`applyTaintStatus`) and runs the old graph BFS as a cross-check that prints `Divergence(graph):` lines.
- `ProbeLean/VerifyInternal.lean`: parses sorry warnings from build output for the build-log cross-check.
- `ProbeLean/Coimport.lean`: preflight check that finds duplicate declarations across project modules in `.olean` headers before import.
- `ProbeLean/Environment.lean`: Lake project detection, subprocess commands (`runCmd`, `runLakeCmd`), build cache, `ProjectModule` discovery.
- `ProbeLean/NixEnv.lean`: Nix environment detection (`NixMode`, `detectNixShell`, `isNixAvailable`).
- `ProbeLean/Metadata.lean`: envelope metadata from git and `lakefile.toml`, and output path construction.
- `ProbeLean/Loader.lean`: loads probe-lean output files, bare-dict or enveloped.
- `ProbeLean/Types.lean`: all data structures and JSON serialization.
- `ProbeLean/View.lean`: the `viewify` command (filters atoms → molecules for the web UI).
- `ProbeLean/Attrs.lean`: shared tag attributes (`@[primary_spec]`, `@[externally_verified]` and four classification tags that probe-lean emits in `attributes` but does not interpret).
- `ProbeLean/Version.lean`: the version constant, generated from `lakefile.toml`.

[docs/schema.md](docs/schema.md) defines every output field, including `dependencies`, `specs` and the `codomain-*` facts. [docs/verification-status.md](docs/verification-status.md) describes how the walk decides `verification-status`.
